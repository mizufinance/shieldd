# Quick native Transfer hash assessment

A wider Anemoi construction is a plausible circuit improvement, but there is **no demonstrated20% complete-proving win or safe drop-in replacement**. Keep the measured~2.11s native prover. If hash research resumes, start with one reviewed width-six/rate-five construction and exact compiled costs; do not generate keys from this accounting.

Cubing is not a permutation here: gcd(3,p−1)=3; the fifth power has gcd(5,p−1)=1.

The Anemoi estimates follow the designers' [round table and Flystel relation](https://anemoi-hash.github.io/): six square rows per column per round with a directly constrained fifth-root hint. Two y-squares, two intermediate root powers and two square rows for the final product establish the relation. Six new columns per cell are possible with direct constraints. A generic witness-plus-equality API can add rows/columns; final padding, constant folding, linear outlining, matrix nonzeros and witness root-exponentiation cost are unmeasured. These estimates are not an implemented secure hash. Upstream's published Fr modules provide widths2and4; a width6instantiation needs parameter generation and validation.

Parameter review is material. [Improved Resultant Attack](https://eprint.iacr.org/2025/259) reports stronger theoretical attacks on Anemoi and other designs. Its full-round CICO estimates for some narrow variants fall below their claimed128-bit level. Old library comments are insufficient assurance. Width6also requires current cryptanalytic review; neither a favorable row estimate nor one attack estimate certifies it. No reduced-round candidate is proposed.

Poseidon2 is less compelling for this square-R1CS target. Its [design](https://eprint.iacr.org/2023/323) chiefly improves linear layers. With comparable S-box counts, that can reduce native work and matrix density, but does not automatically remove the nonlinear square rows dominating this count. No validated parameter set or measured benefit for the exact width6Fr configuration was established here. Jive is a compression mode around a permutation, not an extra independent round-count saving; its arity, domain binding and output mode must be designed explicitly.

The width6estimate saves37,536rows, about19.60%of circuit rows, **not19.60%of proving time**. It remains above131,072, the next smaller domain in the implemented single-removed-coset family. Reaching that size needs60,444rows saved, or73.49%of current hash rows. An intermediate163,840domain would need27,676rows saved and might fit this estimate, but requires new multi-coset domain arithmetic, setup/quotient/opening logic and review. It is not implemented or automatically safe. With M unchanged, fewer witness columns and cheaper solving can still help; the degree-dependent quotient/opening work remains.

As a rough term-count scenario only, assume37,536fewer active witness terms and unchangedM: total major MSM terms drop from977,936to940,400(3.84%). A new163,840domain would drop that count to809,328(17.24%), before fixed FFT/bridge costs and different hash witness costs. This does not substantiate a20%complete-API gain. B's separate377circuit has224,778square rows/M229,376 and needs28,170rows saved to reach196,608; its hash contribution was not measured by this C inventory, and applicable B changes must also update Groth16 A.

Existing exact hash reuse found no duplicate calls. Current alpha5already uses two squares plus a general product; replacing that product by a difference-of-squares identity still costs two square rows unless additional exact operand squares are reusable. No source evidence supports a broad compiler-only halving. No hash setup, proof, new benchmark, production dependency change or formal certification ran for this quick assessment. Any actual hash replacement changes commitments, tree roots, statements and encodings and needs a distinct protocol identity while preserving all compliance/privacy obligations.
