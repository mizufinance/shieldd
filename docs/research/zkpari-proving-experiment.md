# Transfer proving-time experiment

Prepared 2026-09-13 for **Assess shieldd performance gains**. This is an
experiment brief, not measured results or authorization to replace production
cryptography. Implement and measure desktop first, then repeat on physical phones.

## Question and scope

Can an optimized zk-PARI prover approach or beat current Groth16 wallet proving
latency, and does adopting Commonware's native stack improve that outcome?

Compare three complete ways to prove the same Shieldd Transfer behavior. Optimize
only proving time. Exclude SnarkPack aggregation, verifier timing, batch-size
sweeps, network simulation, consensus latency and TPS. Verify proofs as a
correctness gate outside the proving timer. Retain zk-PARI's independently
generated proofs and batch-verification architecture; do not obtain faster times
by dropping zero knowledge, weakening statement binding or outsourcing witnesses.

The motivating analysis, algebra and source references are in
[Reducing Shieldd zk-PARI proving time](zkpari-proving-analysis/report.md).
Its proposed optimizations have not yet produced measured speedups.

For B, check equivalence to the exact original relation, including constant and
public-wire mapping, derived witnesses and public-input outlining. For C, write
an explicit mapping from each current constraint obligation to its native
implementation before timing. Curve-dependent hashes, points, addresses and keys
will differ; compare application semantics and within-candidate native/circuit
agreement, not cross-curve byte equality. Do not weaken bit widths or checks to
fit a new scalar field. Carry over relevant negative and boundary cases.

C must select and document a suitable prime-order circuit group native to the
BLS12-381 scalar field, plus hashes, encodings and required group operations.
Evaluate Commonware's available primitives first; document any missing operations
or security requirements before choosing the replacement. Keeping the exact
Decaf377 arithmetic inside the new circuit is a separate non-native design and
must not silently stand in for the intended native stack. Keep any external
Decaf377 use only where the full binding to the new relation remains correct.

Check the pinned Commonware API's committed-input and public-input requirements.
Account for commitment construction and opening preparation on the prover path.
Do not bypass transcript binding or insert an unexplained dummy input to make a
different statement appear comparable. Document unavoidable protocol differences.

Before collecting final samples, establish positive and negative proof checks for
each candidate, key/statement mismatch rejection and malformed-input rejection.
Verify every measured proof after stopping its proving timer. An invalid proof
invalidates the sample and blocks a candidate result; it is not a fast datapoint.

## Optimization work before the final comparison

For B, implement and retain a small sequence of attributable checkpoints:

1. Prepare the relation, key association, derived-wire mapping and reusable
   immutable domain data once. Remove repeated synthesis, conversion and
   diagnostic traversals from each request while retaining input validation and
   equivalent invalid-assignment rejection. Keep private witness state and fresh
   masking randomness separate for every proof.
2. Lower squares, affine-related products and linear rows directly. The static
   inventory predicts about 241,625 Square-R1CS rows instead of 326,795, crossing
   from a 524,288-point domain to 262,144. Check the actual emitted relation and
   regenerate its development keys; do not report this estimate as a measurement.
3. Profile and optimize the remaining polynomial work: avoid duplicate transforms
   when squaring, repeated interpolation and redundant public contributions where
   algebraically valid. Preserve the pinned zero-knowledge construction.
4. Optimize remaining MSM and allocation costs where the profile warrants it.
   Check the actual MSM implementation, rather than assuming single-point GLV
   acceleration also accelerates MSMs. Include table preparation in first-use
   timing and retain memory use as a feasibility constraint.

Apply appropriate prepared-state, compiler and prover optimizations to C too;
reuse upstream implementations where available. It must include an optimized
real Transfer relation, not an unoptimized first port or a small payment demo.
Investigate fresh-process key loading for both B and C as well as warm proving.
Any faster artifact loader must preserve required validation and artifact trust
boundaries; never equate unchecked decoding with an equivalent optimization.

Use the old unoptimized zk-PARI result as a diagnostic reference, not a fourth
headline candidate. Run short, same-host before/after diagnostics for changed
phases; reserve the full sample matrix for the finalized candidates. Do not run
a Cartesian product of curves, groups and libraries.

If a source-circuit or generic optimization could improve Groth16 as well, add a
matched A-with-that-change control and report its effect separately. Keep the
requested current-A baseline visible. The Square-R1CS lowering specifically
removes zk-PARI conversion overhead; it is not a Groth16 domain-halving claim.
A B-versus-C result measures the whole stack and circuit change, not the isolated
effect of BLS12-381. Add a targeted control only if needed to attribute a result.

## Readiness gate before final measurement

Candidate C must receive a targeted native-circuit design review, not only prover
kernel tuning. Its initial port uses a width-three/rate-two Poseidon sponge for
every input length, while the existing gnark circuit has arity-specific
Poseidon377 configurations. Count hash permutations and Square-R1CS rows by
component before choosing a remedy. Assess appropriate wider, arity-specific
BLS12-381-field hash configurations only with justified parameters and preserved
domain separation/bindings; do not copy constants between fields or reduce rounds
to improve a timing. Alternative parameters change commitments and development
keys, and require native/circuit agreement and full semantic gates again.

Likewise, attribute native group-operation costs and assess square-friendly
addition/doubling, fixed-base specializations and reuse of already constrained
decompositions or subgroup facts for the exact same bound variables. Preserve
canonicality, subgroup, identity and exceptional-case handling. Raw general
product counts alone do not establish that the gadget design is optimal. Use a
bounded component cost inventory and the strongest justified intervention rather
than a hash/curve/window sweep. Preserve the initial full-proof checkpoint.

Selective reuse is also in scope: transfer field-independent prover/compiler
ideas between B and C when applicable, and record when an optimization is already
present in B. Commonware's blst BLS12-381 group implementation cannot operate on
BLS12-377 points as a drop-in backend. Reusing its low-level ideas would require
a correct BLS12-377 implementation and fresh evidence, not mixing curve types.
Do not add a fourth headline candidate or expand the compact final timing matrix
merely to demonstrate portability. Keep any additional work driven by measured
cost and semantic equivalence.

Maintain an optimization ledger for B and C, tied to exact source and build
identities. For each material bottleneck, record its measured share, the proposed
change, correctness evidence, matched before/after timings, and whether the change
was retained or rejected. A rejected optimization is useful evidence; do not
select individual fast samples or change the baseline to manufacture a win.

Before freezing either optimized candidate for the final matrix, establish:

- Complete six-scenario Transfer proofs and cross-component negative checks,
  including C's documented semantic mapping and native primitive parameter checks.
  Component proofs alone do not pass this gate.
- A profile of complete warm and first-use APIs, with witness work and required
  boundary costs included, as well as kernel attribution. Demonstrate that
  immutable preparation and repeated circuit construction are outside the warm
  path where legitimately reusable, and charged to first use.
- Measured investigation of the dominant remaining costs. B's initial profile
  places approximately 90% in commitment/opening MSMs: investigate appropriate
  MSM algorithms, endomorphism decomposition, fixed-base reuse and allocation/
  scheduling choices before treating it as optimized. These are alternatives
  to evaluate, not assumed gains or required changes regardless of evidence.
  Profile the complete C circuit separately; its bottlenecks may differ.
- No unresolved known avoidable dominant cost with an untested concrete remedy.
  Record why promising alternatives were rejected, or identify a remaining
  blocker and label measurements preliminary. This is a practical readiness
  criterion, not a claim that the implementation is globally optimal.
- A fresh matched Groth16 control under the same timing boundaries and worker
  limits, with shared optimizations controlled as described above. Preserve
  randomness, input/key checks, zero knowledge and the complete statement.
- Frozen candidate identities and benchmark settings after tuning. Use new
  measurement samples for the final comparison, separate from tuning samples.
  Re-profile on each phone and reassess desktop-specific tuning before freezing
  its mobile candidate; include table preparation and memory feasibility.

Final samples must run without competing heavy work or diagnostic profiler
overhead. Report initialization/warm tradeoffs and measurement uncertainty. Do
not postpone measurement indefinitely in pursuit of speculative optimizations,
or impose a requirement that zk-PARI must beat Groth16 to finish the experiment.

## Timing boundaries

Primary measurements are wall time for one transaction proof at a time:

| Measurement | Start and finish | Treatment of initialization |
| --- | --- | --- |
| Prepared warm proof | Complete logical witness input available to the production-shaped API → serialized proof and public statement available | Circuit and key already loaded; all per-proof work included |
| Fresh-process first proof | Start the prover process/application's proof initialization → same completed output | Includes loading, required artifact checks, preparation and first proof |

Warm time includes witness construction/solving, required commitments/openings,
language/FFI transport, canonical decoding, assignment mapping, fresh randomness,
proving and serialization. Count each operation once. Preserve real packaging
costs; avoid making an obsolete diagnostic JSON bridge the permanent architecture
of B, or hiding a necessary language boundary outside its timer. Separate
benchmark-controller transport from the measured API and label any remainder.

Record non-overlapping stage times for diagnosis, including witness/solver,
transport/mapping, polynomial work, MSMs and encoding where instrumentable. The
whole API wall time decides the outcome; kernel-only timing is supplementary.
Report profiler-enabled diagnostics separately if instrumentation changes runtime.

Exclude installation, downloads, offline trusted setup/key generation and offline
circuit compilation from latency. Report their exclusion explicitly. If a deployed
candidate compiles or derives tables at runtime, include that work in first use.
Pre-generated artifacts must be available locally for all three candidates.

A fresh process does not imply a cold OS file cache. Record process lifecycle and
cache conditions; do not claim cold-storage latency or flush the user's global
caches. Memory and key size are feasibility metadata, not additional optimization
targets. Record failures, OOM and unsupported devices rather than omitting them.

## Run 1 — Desktop, without a phone

Finish correctness and implementation first. Use the same physical host for all
three release builds; record hardware, OS, compiler flags, dependency revisions,
circuit sizes/domains, keys, source/patch hashes and timing boundary versions.

- Use one common two-worker profile and one representative standard Transfer
  fixture for all three candidates. Retain all six scenarios for correctness;
  they do not each need repeated timing when they share one circuit and key.
  Respect repository resource limits and keep one heavy job active.
- Per candidate, collect two untimed warmups and five measured complete warm
  proofs, with fresh proving randomness. Rotate candidate order across paired
  blocks and use the same logical inputs. Do not time competitors concurrently.
- Collect one fresh-process first proof per candidate, including required key
  checks and preparation. Label it a single observation, not an estimate of
  typical cold latency. Keep startup diagnostics available to explain its cost.
- Establish controlled cooldown and background-load rules. Retain slow samples;
  only exclude documented interruptions under a declared rule and rerun the
  affected paired block. Preserve the excluded data and reason.

The final comparison is **18 measured proofs per device**: three candidates
times five warm proofs and one first proof, plus six untimed warmups. The final
benchmark should be short once optimization is complete. Avoid scenario, worker
count and batch-size sweeps. Add only a targeted check when a distinct circuit,
lazy initialization path, unstable timings or a close result creates an actual
unanswered question. Explain the reason before expanding; do not automatically
increase the sample count until a preferred winner appears.

Optimization diagnostics are separate, small, targeted runs; they must not grow
into a second exhaustive benchmark campaign. No 4,096-proof corpus is required.
Do not use an old timing cell as the final A control unless its source, host,
fixtures, timing boundaries and execution conditions match this experiment.

Publish the desktop comparison before beginning the phone campaign. Carry all
three candidates forward if they can run correctly; desktop rank alone must not
eliminate a candidate whose relative performance may change on ARM phones.

## Run 2 — Physical phone proving

Use a physical iPhone and a physical Android phone where available, prioritizing
devices representative of supported users. Record exact models, SoCs, RAM, OS,
build mode and versions. Missing devices are explicit gaps. Emulators, desktop
ARM timings and two-worker desktop runs do not complete the phone phase.

Package all three candidates through production-shaped mobile APIs with on-device
witness handling and local proof creation. Include the actual Go/Rust/FFI and
serialization costs. No simulator, debug build, remote prover or server-assisted
witness processing may stand in for a measured on-phone candidate.

Repeat the compact 18-proof comparison on each available physical phone, with
two untimed warmups per candidate and a fresh application for its first-proof
observation. Use one common two-worker profile where supported; otherwise choose
and document one common supported profile. Include thermal state, battery/power mode
and charging state. Balance candidate order across controlled sessions with
cooldown so one candidate does not inherit another's thermal throttling.

Use the finalized desktop revisions as the first mobile comparison. Mobile-specific
optimizations are allowed, including SIMD, allocation and scheduling work, but
record them as a separate revision and rerun its relevant controls. Distinguish
a single-proof latency from thermal slowdown during repeated use. Key loading
and required validation remain inside first-proof timing on phones.

If a candidate fails to compile, exceeds device memory or cannot finish reliably,
record that result and cause. Do not substitute a smaller circuit or omit it
from the comparison. Report a missing platform as pending, not a measured loss.

## Results and decision

Deliver reproducible commands, exact build/artifact identities, raw samples,
correctness results, phase breakdowns and one concise report. Show all three
candidates together for each device, with warm median, observed minimum/maximum,
all five raw warm values and the single first-proof observation. State the common
worker profile and representative scenario. Do not report p95 or robust tail
claims from this small sample.

Report descriptive ratios of warm medians, including A/B, A/C and B/C; define a
ratio above one as the denominator being faster. With five samples, avoid
strong confidence claims or mandatory bootstrap analysis. Do not pool devices.
Use one compact comparison table; charts are optional. Show first-proof costs
separately, and call close or noisy rankings inconclusive unless a small targeted
follow-up resolves them.

Answer how much of the current zk-PARI regression B recovers, whether C improves
on B, and whether either reaches A on desktop and on each tested phone. If gains
overlap measurement uncertainty, report the result as inconclusive. Explain
tradeoffs between first and repeated proofs rather than declaring one winner
from a kernel benchmark. State which optimizations also benefit Groth16.

This experiment makes a proving-performance recommendation. It does not establish
production readiness, formal coverage or measured network performance.
